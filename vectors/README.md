# Shared test vectors

Frozen golden data consumed by both implementations: the TypeScript tests in
`packages/ur/tests/` and the Rust tests in `crates/bcur/tests/` and
`crates/bcur/src/` read exactly these files. Do not reformat, re-wrap, or
normalize them; any change is a deliberate contract change and must land in
both languages in the same commit.

Line files (`.txt`, `.hex`) are data-only: UTF-8, LF line endings, a trailing
newline, and no `#` header comments — provenance lives in this README instead.
Runners must not need comment skipping. If a vector mismatch is ever an
implementation bug rather than a stale golden, that is what these files are
for: they pin behavior, not the implementations' bugs.

## Provenance

- `ur-rs/` — golden tables from [ur-rs](https://github.com/dspicher/ur-rs)
  0.5 (MIT). `multipart-20.txt` additionally matches the URKit/bc-ur 20-URI
  table. See `THIRD_PARTY.md`; only goldens are vendored, no source.
- `ur/published-singles.txt` — published single-part UR goldens from
  BCR docs, bc-ur docs, and the ur-rs Wolf/50 example.
- `official/published-from-refs.txt` — sorted-unique extract of every `ur:`
  literal quoted in the pinned URKit/bc-ur reference files. Regenerate with:

  ```bash
  scripts/vectors/extract-published-urs.sh > vectors/official/published-from-refs.txt
  ```

- `bytewords/`, `fountain/`, `ur/k1.json`, `typed/`, `limits/` — contract
  vectors authored for this repository's ur.js + bcur interop suite.
- `keystone/` — `ur:crypto-output` / `ur:crypto-account` literals extracted
  from [KeystoneHQ/ur-registry](https://github.com/KeystoneHQ/ur-registry)
  (Apache-2.0) `__tests__/CryptoOutput.test.ts` and
  `__tests__/CryptoAccount.test.ts` at commit
  `bd8f408127c420f723222c1934c5666873a94c3e`, used as a second source for the
  v1 descriptor forms. Keystone's encoder omits the `crypto-output` tag on
  `crypto-account` entries and writes cosigner keys without the `410` tag;
  the reader accepts both spellings (see `script-expression.ts`). No source
  code is vendored — see `THIRD_PARTY.md`.
- `consensus/next-double.json` — generated by
  `bun scripts/vectors/generate-next-double.ts`, which cross-checks every
  expected `f64` bit pattern against Python's exact `float(v) / 2**64`
  conversion (`"crossCheck": "python float()"` in the source envelope). Each
  case is `{ rawHex, nextDoubleBitsHex, nextIntRange: [low, high], nextInt }`:
  `nextDoubleBitsHex` is the IEEE-754 bit pattern of `raw / 2^64` with
  round-to-nearest-even, and `nextInt` is `floor(d * span) + low` clamped to
  `high` (the clamp fires when `d` rounds to 1.0, i.e. raw >= 2^64 - 2^10).

## Official compliance vectors

`official/` is generated data, not hand-written. Regenerate with:

```bash
bun scripts/vectors/extract-official.ts
```

The script fetches the pinned upstream files (retrying transient network
errors), extracts anchored code blocks / test cases, fails loudly when any
expected anchor or count is missing, and cross-checks values that appear in
more than one source (priority: BCR-2024-001 > URKit > bc-ur). Output is
byte-stable across runs. Pinned revisions:

- BlockchainCommons/Research `e4a4fbb186e2e7625ccdf7149aec4f0a5adaf850`
  (`papers/bcr-2024-001-multipart-ur.md`, `bcr-2020-012-bytewords.md`,
  `bcr-2020-005-ur.md`, `bcr-2020-006-urtypes.md`, `bcr-2020-007-hdkey.md`,
  `bcr-2020-011-sskr.md`)
- BlockchainCommons/URKit `ebba59b2e1538cb368d98147dd58c452e6d1dc47`
  (`Tests/URKitTests/{BytewordsTests,FountainCodesTests,TestUtils,URTests}.swift`)
- BlockchainCommons/bc-ur `4479fb81b2350ae8bafa042a5572b9c64c2c32ca`
  (`test/test.cpp`, `test/test-utils.cpp`, `test/test-utils.hpp`)

Every JSON file carries a `source` envelope recording the document, pinned
revision, path, and the other sources the value was cross-checked against.

### Layout under `official/`

| File                        | Capability                | Cases                                            |
| --------------------------- | ------------------------- | ------------------------------------------------ |
| `mur/crc32.json`            | `consensus.crc32`         | `inputUtf8`/`inputHex` → CRC-32 hex             |
| `mur/rng.json`              | `consensus.xoshiro`       | Xoshiro ops: `nextMod`, `nextInt`, `nextData`    |
| `mur/fragment-length.json`  | `fountain.fragment-length`| message/max → fragment length                    |
| `mur/partition.json`        | `fountain.partition`      | message → padded fragments                       |
| `mur/degree.json`           | `consensus.sampler`       | degree chooser + weighted sampler streams        |
| `mur/shuffle.json`          | `consensus.shuffle`       | remove-shuffle prefixes + continued rounds       |
| `mur/chooser.json`          | `consensus.chooser`       | sorted fragment indexes per sequence number      |
| `mur/part-cbor.json`        | `fountain.part-cbor`      | `Part` fields → deterministic CBOR               |
| `mur/encoder.json`          | `fountain.encoder`        | part streams + `isComplete`                      |
| `mur/decoder.json`          | `fountain.decoder`        | round-trip with `firstSeqNum`                    |
| `bytewords.json`            | `bytewords.codec`         | standard/uri/minimal + error cases               |
| `ur/single.json`            | `ur.parse` / `ur.decoder` | single-part URs (incl. BCR-2020-005 worked)      |
| `ur/multipart.json`         | `ur.encoder` / `ur.decoder` | multi-part URs (`partsFile` refs shared goldens) |
| `registry/*.json`           | `registry.*`              | `{name, urType, cborHex, ur, tag?, diagnostic?}` |

Messages generated by the shared `makeMessage(seed, length)` helper are
described (`{"message": {"seed": "Wolf", "length": 1024}}`), not inlined.
The `rng.json` `op` field mirrors the source tests: `nextMod` (raw `next()`
modulo `args.modulus`), `nextInt` (`args.low`..`args.high`), and `nextData`
(`args.length` bytes per draw).

The sources only assert that invalid input fails; the `error` field records
this project's error code for that failure, which both implementations must
return.

### Runners

- TypeScript: `packages/ur/tests/vectors/{mur,bytewords,ur,registry}.test.ts`.
- Rust public API: `crates/bcur/tests/official/{main.rs,bytewords.rs,mur.rs,ur.rs}`.
- Rust consensus internals + cases needing the crate-private message
  generator: `crates/bcur/src/official_vectors.rs` (a `#[cfg(test)]` module).

### Notes and known gaps

- `firstSeqNum` maps onto `FountainEncoderOptions.first_sequence`
  directly; `minFragmentLength` is asserted only where the bound does not
  bind. Tracked as F-11.
- Expected failure: the historical BCR-2020-006 seed vector tags the creation
  date as `100(...)` while the current seed codec accepts CBOR date tag `1`
  only — `test.fails("... [F-01]")` in `registry.test.ts`.
- Skipped upstream tests (no public surface): buffer XOR and SHA-256
  known-answer tests, Bytemoji/`identifier`/`checksumWords`/`encodedLength`
  helpers (deferred to R2), and registry types not yet implemented (eckey,
  address, descriptors, crypto-account, crypto-output — deferred to R3).

## Registration

`scripts/parity/check.ts` requires every file under `vectors/` to be
registered in `parity.json` and cited by at least one of the capability's
test files; stable capabilities must have tests on both sides.
